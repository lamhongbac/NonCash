### 1.5 Voucher display fields exposed end-to-end (Epic 8 pass-through)
Display definition (cover image, icon, T&C, display name, short description, brand color, valid days) **lives on the plan** — entity/service already supported it; the gap was API DTOs + Web form. Now closed:
- `src/NonCash.API/DTOs/PlanDtos.cs` — 6 optional display fields on `CreatePlanRequest` / `UpdatePlanRequest` / `PlanResponse` (backward compatible).
- `src/NonCash.API/Controllers/VoucherPlansController.cs` — pass-through in Create/Update/MapToResponse.
- `PlanCreate.razor` — new **"Display (Mobile App / Web)"** section: DisplayName (≤40), ShortDescription (≤80), BrandColor, Valid Days, T&C, and **cover/icon uploads** (cover 1200×630 ≤2MB, icon 128×128 ≤500KB) posting to `api/v1/upload/image`.
- `src/NonCash.Web/Components/Shared/VoucherCard.razor` — resolves relative image URLs at display time.
- MudBlazor 9.4 gotcha: `MudFileUpload` has **no `ActivatorContent`** — use `<CustomContent Context="upload">` + `OnClick="@upload.OpenFilePickerAsync"`.

### 1.6 Image upload pipeline clarified + local-URL fix
- Route `POST api/v1/upload/image` is composed from attributes in `ImageUploadController` (`[Route("api/v1/upload")]` + `[HttpPost("image")]`) — it never appears as one grep-able string.
- Storage is behind `IImageStorageService`, toggled by config `MediaServiceConfig:ImageStorage`:
  - `"MSA"` (appsettings.json / prod-pilot) → remote MSA media service, image served from CDN `http://45.119.87.247:8001/cdn`.
  - `"Local"` was previously set in `appsettings.Development.json`, which is why earlier DEV uploads landed in `src/NonCash.API/wwwroot/uploads/` instead of MSA. **Changed to `"MSA"`** so the shared DEV environment uses the same storage as pilot/production.
- Fixed `ResolveImageUrl` (in both `VoucherCard.razor` and `PlanCreate.razor`): `/uploads/...` URLs now resolve against the **API base URL**, everything else against the CDN. Without this, local-mode images would never render.

### 1.7 Plan save crash fixed (`Cannot write DateTime with Kind=Local ... only UTC is supported`)
- `src/NonCash.Core/Services/VoucherPlanService.cs`
- Npgsql requires `Kind=Utc` for `timestamptz`. All six plan dates (`PlanDate`, `ExpiryDate`, `PublishDate`, `ValidFrom`, `ValidTo`) now pass through `AsUtc()` in Create **and** Update.
- Deliberate choice: `DateTime.SpecifyKind` (keeps the calendar date the user picked) instead of `ToUniversalTime()` (would shift the day across timezones).

### 1.8 Distribution mechanism confirmed (design walkthrough, no code change)
- Distribution = **DB ownership assignment**, not message delivery. `PromotionService.DistributeAsync`: normalize phones → find-or-create Customer + placeholder MemberAccount → assign one voucher per member + `VoucherDistribution` audit row, all atomic.
- Customers see vouchers by **pull**: member portal login (phone) or partner app via Integration API (wallet-by-phone).

### 1.9 Email vs Zalo analysis → decision
- **Decision: Email first (free, already built), Zalo ZNS second (start OA onboarding early — 2–4 weeks lead time), SMS excluded (cost ~700–900 VND/msg).**
- Key constraint: promo lists are phone-only → Zalo (phone-keyed) has the best reach; email coverage grows as members register (see 1.10).

### 1.10 NEW FEATURE: mandatory email + distribution notification channels
- **Member registration email is now required** (`MemberRegistrationController` + `MemberRegister.razor`): required + format-validated; registration also back-fills email onto placeholder customers created by earlier distributions.
- New `NotificationChannel` flags enum (`None / Email / Zalo / Both`) in `INotificationService.cs`, plus `NotifyVoucherReceivedAsync(VoucherReceivedNotification)`.
- `EmailNotificationService`: sends the voucher-received email; skips (logged) when no email on file. **Zalo flag currently logs "Zalo ZNS not yet onboarded" — stub awaiting OA approval.**
- `PromotionService.DistributeAsync` gained `notifyChannels` param (default Email); notifications run **after** the atomic save, best-effort — can never fail the distribution.
- API: `promote` accepts form field `notifyChannels`; `promote/json` accepts `"notifyChannels": "Email"|"Zalo"|"Both"`.
- Integration API (`/integration/distribute`) passes `None` — partners notify their own members.
- UI: Batch Promotion panel in `PlanVouchers.razor` has "Notify recipients via: Email / Zalo / Both" radios (Email default).
